D. React Render Audit

Find and fix excessive re-renders.

Inspect:
- Studio root component
- Transport component
- Mixer
- Sequencer grid
- Piano roll
- Arrangement timeline
- Visualizer
- Meters
- Sample browser
- Project browser
- Inspector panel
- Settings modal
- Any context providers

Common problems to find:
- transport position stored in global React state updating too often
- meter values updating React state every animation frame
- visualizer data triggering whole-app re-renders
- large project object passed through context causing every child to re-render
- inline objects/functions causing memoized children to re-render
- arrays rebuilt every tick
- useEffect dependencies causing loops
- timers or animation frames not cleaned up
- state updates during render
- parent component storing too much rapidly-changing state
- sequencer cells all re-rendering every step

Required fixes:
- Keep high-frequency audio timing out of React state.
- Use refs for fast-changing transport/playhead/meter internals.
- Throttle UI updates for meters/playhead.
- Use React.memo on expensive child components.
- Use useMemo/useCallback only where it prevents real expensive rerenders.
- Split large context into smaller contexts or stores.
- Ensure sequencer step playback does not rerender the entire app.
- Ensure visual meters update at controlled FPS, not unlimited.
- Prevent panels not visible from rendering heavy content.
- Lazy-load heavy panels if practical.

Target:
- During playback, React should not rerender the entire studio every tick.
- Mixer meters should not force mixer controls to rerender.
- Playhead animation should not force arrangement clips to rerender.
- Sequencer active-step highlight should be isolated.

E. Audio Engine and Tone.js Audit

Inspect all Tone.js and Web Audio usage.

Find:
- multiple AudioContexts being created accidentally
- multiple Tone.Transport schedules stacking after project reload
- duplicate event scheduling on every render
- Tone nodes created inside React render functions
- Tone nodes created repeatedly without dispose()
- samplers/synths/effects never disposed
- analyser nodes never disconnected
- meters never stopped
- audio graph rebuilt too often
- transport event IDs not stored/cancelled
- stuck notes after stop
- old project tracks still scheduled after loading new project
- sample buffers duplicated in memory
- effects chains recreated unnecessarily
- master bus duplicated
- metronome scheduled multiple times

Required fixes:
- AudioEngine must be singleton-like for the app session.
- Only one AudioContext/Tone context should exist unless there is a documented reason.
- Store all scheduled Transport event IDs.
- Clear/cancel old scheduled events before rescheduling.
- Dispose deleted synths, samplers, effects, analysers, meters, and gain nodes.
- Add a full panicStopAll() that:
  - stops transport
  - cancels scheduled events
  - releases all notes
  - disconnects temporary nodes
  - clears active voices
- Add cleanup methods for:
  - unloadProject()
  - removeTrack()
  - replaceInstrument()
  - replaceKit()
  - destroyAudioEngine()
- Avoid creating Tone nodes inside React component render bodies.
- Avoid reinitializing audio on every route/modal/open-close event.

F. Scheduler and Playback Stabilization

Audit playback scheduling.

Find:
- setInterval-based audio triggers
- requestAnimationFrame-based audio triggers
- React state-driven note triggering
- duplicate Tone.Transport callbacks
- unsafely rescheduling during playback
- pattern changes causing full reschedule storms
- unbounded event queues

Required fixes:

- Use the exact scheduled time argument when triggering notes.
- Batch pattern rescheduling.
- Debounce expensive reschedule operations.
- Avoid rescheduling entire project for tiny UI changes unless necessary.
- If live editing during playback is supported, make it incremental.
- Keep visual playhead separate from actual audio schedule.
- Add guardrails so playback cannot start twice.
- Add state machine:
  - stopped
  - starting
  - playing
  - paused
  - stopping
  - error

G. Visualizer and Meter Optimization

Visualizers and meters are common lag monsters. Audit them aggressively.

Find:
- multiple requestAnimationFrame loops
- animation loops running while panel hidden
- canvas drawing at full speed unnecessarily
- huge FFT sizes
- React state updates from every analyzer frame
- waveform/spectrum components not cleaned up
- visualizer rendering during export/import when unnecessary
- meter components causing parent rerenders

Required fixes:
- Centralize animation frame management.
- Stop animation loops when components unmount or are hidden.
- Cap visualizer FPS:
  - meters: 20-30 FPS
  - spectrum/oscilloscope: 30 FPS max

- Use canvas drawing directly instead of React state for high-frequency visuals.
- Reduce analyser FFT size if excessive.
- Avoid creating new typed arrays every frame when reusable buffers work.
- Throttle meter calculations.
- Turn off nonessential visuals during heavy operations.
- Add “Reduce Motion / Performance Mode” setting.

R. Strong Guidance on Likely Fix Areas

Pay special attention to these likely offenders:

1. Transport/playhead state
   If playhead position updates global React state 30-60 times per second, isolate it.

2. Mixer meters
   If each meter update rerenders the mixer or track components, move meter drawing to canvas or refs.

3. Visualizers
   If multiple requestAnimationFrame loops exist, centralize and stop hidden loops.

4. Audio node lifecycle
   If Tone nodes are created repeatedly and not disposed, fix immediately.

5. Scheduled events
   If Tone.Transport events are stacking after every edit/load/play, store IDs and clear them.

6. Waveform rendering
   If all waveforms render at once, lazy render visible ones only.

7. Autosave
   If autosave serializes the full project too frequently, debounce and split blobs from metadata.

8. Sample import
   If decoding/processing blocks the main thread, chunk it or move preprocessing to a worker.

9. Service worker
   If stale caching causes old code/assets to fight new code/assets, fix versioning and cleanup.

10. CSS effects
   If dense grids use heavy shadows, blur, filters, or animated glows, simplify them.
